● I think I found why OVH disables the task without leaving anything in your
  log. I made the fix, but it isn't verified on OVH yet.

  Why there's no error log: in commit 8cd2ff9, bin/cron-bootstrap.php printed
  every line with fwrite(\STDOUT, ...). The STDOUT constant only exists when PHP
  runs as the command-line (CLI) program. OVH's scheduler can run scripts with
  the CGI version of PHP instead. There, the first START line crashes with
  "Undefined constant STDOUT". The error handler tries to print with the same
  STDOUT, so it crashes too, before writing anything to var/log/cron.log. Your
  manual run used CLI PHP, so it worked and wrote exit=0. I couldn't confirm
  that OVH uses CGI, because CGI PHP isn't installed on this machine.

  What I changed in bin/cron-bootstrap.php:
  - Logs first: it writes a START sapi=... php=... memory_limit=... 
    max_execution_time=... line to var/log/cron.log before doing anything else.
    The sapi value will show whether OVH runs CLI or CGI.
  - No STDOUT: output goes through streams the script opens itself, so it works
    under CLI and CGI.
  - Full output kept: every run writes its complete output (exceptions, PHP
    fatal errors, stack traces) to var/log/cron-cron-facture.last.log. It's
    written as the run goes, so the file keeps what was printed even if OVH
    kills the process. The same output still goes to OVH's cron logs.
  - No time limit: it calls set_time_limit(0), because CGI PHP doesn't run
    without a time limit by default.
  - End line always written: a summary line is added at the end even after a PHP
    fatal error or an exit(). A START with nothing after it means the process
    was killed for time or memory.

● You were right and I was wrong. On this server, you need native://, not
  smtp://.

  Why: "Connection refused" on smtp.mail.ovh.net:465 means the server blocks the
  connection itself. Your password was never even checked. OVH shared hosting
  generally doesn't let scripts open SMTP connections. PHP's own mail() function
  goes through OVH's internal mail relay instead, and native:// uses that
  relay. This probably also explains the cron failures. When invoices or the
  report email fail to send, mercredi:facture-send returns an error code. After
  10 failed runs in a row, OVH disables the task.

  Test it on the server before changing anything. A real environment variable
  overrides .env.local:
  php -r 'echo ini_get("sendmail_path"), PHP_EOL;'
  MAILER_DSN=native://default php bin/console mailer:test jfsenechal@gmail.com 
  --from=titi@visitmarche.be
  - The first line should print OVH's sendmail command. If it prints nothing,
    native:// won't work.
  - Use --from with an address on a domain hosted at OVH. Without it, the test
    uses from@example.org, which OVH will likely refuse or mark as spam.

  If the mail arrives, put this in .env.local at the project root:
  MAILER_DSN=native://default
  The text after native:// is ignored. native://titi@visit... would work too,
  but default is the usual way to write it. With native://, the password isn't
  needed in this file at all.

  Things to check afterwards:
  - The app's sender address (the "From" of invoices and reports) must also be
    on a domain hosted at OVH.
  - OVH caps how many mails mail() can send per hour. Keep MAILER_HOURLY_LIMIT
    under that cap.
  - Also test the website's mails once (contact form or login link). If the
    website also used smtp://, its mails probably weren't being sent either.

  Want me to change the MAILER_DSN example in DEPLOY.md to native://default, and
  commit that together with the cron bootstrap fix?

  1. ArgumentCountError: the prod cache is stale. The service container in

  rebuilt. On OVH, run:
  php bin/console cache:clear
  If that command fails too, delete the cache folder: rm -rf var/cache/prod.
  Clear the cache after every deploy; otherwise the site and the crons keep
  running on the old container.

  2. Fatal error: ... not allowed to submit mail: the error mail crashes the 
  process. The command failed and logged an error. In prod, monolog then emails
  the log to the webmaster. Over SSH, OVH refuses that email, and the exception
  escapes when PHP shuts down. In a cron job, the same thing would turn any
  logged error into a failed run, and OVH counts failed runs toward disabling
  the task.

  I wrapped the email handler in monolog's whatfailuregroup (new mail_safe
  handler). If the error email can't be sent, the failure is ignored and the
  error is still written to var/log/prod.log. The prod container builds with
  this change. My local attempt to reproduce the crash wasn't conclusive: it
  didn't crash even without the fix, because my setup doesn't hit the same code
  path as OVH. My confidence comes from Monolog's source:
  WhatFailureGroupHandler::close() catches exactly the exception in your trace
  (BufferHandler->close() → DeduplicationHandler->flush()).
