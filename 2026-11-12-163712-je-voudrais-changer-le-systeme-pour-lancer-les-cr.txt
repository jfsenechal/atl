● Recommandation : une commande console lancée par les « Tâches planifiées 
  (CRON) » du manager OVH, via un petit script PHP d'amorçage. C'est ce qui
  remplace proprement l'appel HTTP sur un mutualisé.

  symfony/scheduler, la solution Symfony « idiomatique », ne convient pas ici :
  il lui faut un worker permanent (messenger:consume scheduler_default), et le
  mutualisé OVH n'autorise ni daemon, ni supervisor, ni crontab système.

  Les contraintes du cron OVH, de mémoire (à vérifier dans votre manager) :
  - Fréquence : une exécution par heure au maximum, ce qui colle avec votre
    rythme actuel et le garde-fou de 60 minutes dans FactureCronHandler.
  - Durée : 60 minutes maximum par exécution.
  - Commande : on désigne un fichier PHP, sans arguments. On ne peut donc pas
    écrire bin/console mercredi:facture-send directement, d'où le script
    d'amorçage.

  Ce que je mettrais en place :

  1. Rebrancher mercredi:facture-send sur FactureCronHandler::execute().
     Aujourd'hui la commande duplique une ancienne version de la logique : pas
     de génération de PDF, pas de lot de 40, pas de délai de 60 minutes. Le
     handler est la version à jour.
  2. Ajouter un script bin/cron-facture.php qui démarre le kernel en prod et
     exécute la commande. C'est ce fichier qu'on déclare dans le manager OVH,
     hors de public/, donc inaccessible par le web.
  3. Supprimer la route /cron/launch dans DefaultController. Elle est publique
     et sans authentification : n'importe qui peut déclencher l'envoi.
  4. Ajouter symfony/lock sur la commande, pour éviter deux exécutions
     simultanées.

  Un point à vérifier en parallèle : SendEmailMessage est routé vers le
  transport async (Doctrine), donc les mails sont mis en file et non envoyés
  directement. Je n'ai pas vu ce qui consomme cette file en production (la
  méthode consume() du contrôleur n'a pas de route). Si rien ne la consomme, il
  faut une seconde tâche OVH qui lance messenger:consume async 
  --time-limit=3300, ou repasser les mails de factures en synchrone.

  Voulez-vous que j'implémente les points 1 à 4 ?

● Oui : en console, l'envoi passe exactement par le même chemin qu'en web, rien
  dans le code ne dépend du contexte HTTP. NotificationMailer::sendMail()
  appelle MailerInterface::send(), qui utilise le MAILER_DSN configuré.

  Deux points décident si ça marche réellement chez OVH :

  - Le transport. Si la production est en SMTP (comme votre .env.local ici :
    smtp.marche.be:465), PHP ouvre une connexion sortante, que ce soit en web ou
    en CLI. Comme la route /cron/launch envoie déjà par ce biais depuis le même
    hébergement, il n'y a pas de raison que ça change. Le seul cas douteux
    serait sendmail://default ou native://default, qui dépendent de la
    configuration du PHP CLI ; je n'ai pas accès au MAILER_DSN de production
    pour le confirmer.
  - La file Messenger. Dans config/packages/messenger.yaml, SendEmailMessage est
    routé vers async. send() n'envoie donc pas le mail : il l'écrit dans la
    table messenger_messages, en web comme en console. Le mail ne part que
    lorsqu'un messenger:consume async tourne. Je n'ai rien trouvé dans le dépôt
    qui lance ce worker ; si les factures partent bien aujourd'hui, c'est que
    quelque chose le fait en production ou que la config y est différente.

  Pour lever le doute, deux commandes à lancer sur l'hébergement OVH (en SSH, ou
  via une tâche cron temporaire) :

  php bin/console mailer:test votre@adresse.be   # envoi direct, sans passer par
  Messenger
  php bin/console messenger:stats                # nombre de messages en attente
  dans la file

  - Si mailer:test arrive, l'envoi en console fonctionne.
  - Si messenger:stats montre des messages en attente, la file n'est pas
    consommée.

  Pour les factures, je conseille de toute façon l'envoi synchrone dans la
  commande cron : elle tourne déjà en arrière-plan, par lots de 40, et vous
  marquez envoyeLe juste après l'envoi. Avec la file, une facture est notée «
  envoyée » alors que le mail peut encore échouer plus tard. Cela se fait en
  retirant le routage async de SendEmailMessage, ou en injectant le transport
  directement (TransportInterface) dans le handler.

  Dites-moi ce que donnent les deux commandes et j'adapte l'implémentation en
  conséquence.

  Ce qui a changé

  - Commande mercredi:facture-send : elle délègue maintenant à
    FactureCronHandler::execute() (génération du PDF, lot de 40, délai de 60
    minutes) et envoie le rapport comme le faisait la route. L'option --force
    disparaît, remplacée par --max (40 par défaut) ; le forçage reste porté par
    force_send de l'entité.
  - Envoi synchrone : dans FactureCronHandler, la facture part directement par
    le transport SMTP, sans passer par la file Messenger. Elle n'est marquée
    envoyeLe que si le serveur a accepté le mail.
  - Script bin/cron-facture.php : c'est le fichier à déclarer dans le manager
    OVH. Il lit APP_ENV dans le .env.local du serveur.
  - Route /cron/launch supprimée, ainsi que le template default/cron.html.twig
    et la méthode consume() du contrôleur, qui n'avait pas de route.
  - Verrou : symfony/lock est installé via Flex (LOCK_DSN=flock). Si une
    exécution est déjà en cours, la commande s'arrête sans rien faire.

  À savoir

  - Alertes admin et rapport : ils passent toujours par le Notifier, donc par la
    file async. Si cette file n'est pas consommée en production, vous ne les
    recevrez pas. Dites-moi si vous voulez que je les passe aussi en direct.
  - Bouton admin « lancer » (/admin/facture/send/all/cron/{id}) : je ne l'ai pas
    touché ni vérifié.
  - Verrou flock : il est local à une machine. Si OVH lance les crons sur des
    nœuds différents, il ne protège pas ; le délai de 60 minutes sur
    dateLastSync reste alors le garde-fou.

  Mise en production

  1. Déployer, avec composer install pour récupérer symfony/lock.
  2. Dans le manager OVH, sous Hébergement → Tâches planifiées, créer une tâche
     horaire pointant vers bin/cron-facture.php (chemin relatif à la racine de
     l'hébergement), avec PHP 8.5.
  3. Supprimer l'ancienne tâche qui appelle https://atl-hotton.be/cron/launch :
     elle renverra désormais une 404.
